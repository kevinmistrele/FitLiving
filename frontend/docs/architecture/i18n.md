# Internationalization (i18n)

This base uses `react-intl`. **Translations are owned per feature, not kept in one giant application-wide file.** A feature that has user-facing copy ships its own `en.json`/`pt.json` next to its code; a small root registry merges every feature's messages into the catalog `IntlProvider` actually uses.

## Why per-feature, not one global file

A single `src/i18n/translations.json` for the whole app becomes a dumping ground nobody wants to touch, causes merge conflicts across unrelated features, and makes it impossible to tell whether a key is still used when a feature is deleted. Keeping translations with the feature that owns them means deleting a feature deletes its copy too, and an agent working on one feature never needs to open a 500-line shared JSON file.

## How it's wired

```txt
src/features/<feature>/i18n/
  en.json
  pt.json
  index.ts        # exports `<feature>FeatureMessages = { en, pt }`

src/i18n/
  en.json          # app-level messages genuinely shared by many features (e.g. "common.retry")
  pt.json
  feature-registry.ts   # imports every feature's messages and merges them
  index.ts         # exports the final merged `messages` map + `SupportedLocale`
  locale-context.tsx
  locale-provider.tsx    # wraps children in IntlProvider, owns the current locale
```

`src/app/provider.tsx` mounts `LocaleProvider` once, near the root, alongside `QueryClientProvider`. Nothing else needs to know the merge happened.

## Adding translations to a new feature

1. Create `src/features/<feature>/i18n/{en,pt}.json` with flat, namespaced keys: `"<feature>.<screen-or-context>.<key>"` (e.g. `"auth.signin.title"`, `"welcome.reload"`). Namespacing by feature name prevents key collisions between features that never see each other's files.
2. Create `src/features/<feature>/i18n/index.ts` exporting `export const <feature>FeatureMessages = { en, pt };`.
3. Register it in `src/i18n/feature-registry.ts`: add one entry to the `features` array. This is the one place that legitimately imports across every feature — see the exception in [dependency-rules.md](./dependency-rules.md).
4. Add both locales for every key. A missing key falls back to the id itself (see `useTranslate` below), which is visible enough in review to catch, but don't rely on that — keep `en.json`/`pt.json` in sync.

## Using translations in components

```tsx
import { useTranslate } from '@/hooks/use-translate';

function ReloadButton() {
  const { t } = useTranslate();
  return <button onClick={() => window.location.reload()}>{t('welcome.reload')}</button>;
}
```

- `useTranslate()` wraps `react-intl`'s `useIntl().formatMessage`; call `t('feature.key')` instead of importing `useIntl` directly, so the fallback-to-id behavior stays consistent everywhere.
- `t` takes an optional second argument for interpolation values: `t('welcome.greeting', { name })`.

## What NOT to translate

Only static UI copy the app owns goes through `t()` — labels, headings, button text, empty/error/loading strings. **Data returned by the API is not translated client-side**: if `message.title` comes from a query response (see `src/features/welcome/components/welcome-screen.tsx`, where the loading/error/button strings use `t()` but `message.title`/`message.description` are rendered as-is), that's the API's/backend's responsibility, not `react-intl`'s. Mixing the two makes it unclear which strings are safe to rename/remove as translation keys and which are live data.

## Switching locale

```ts
const { currentLocale, changeLocale } = useLocale();
changeLocale('pt');
```

`useLocale()` reads/writes the current locale. `LocaleProvider` resolves the initial locale in this order: `?locale=` query param → `localStorage` → browser language → `en` default. Persisted choices are stored under the `locale` key in `localStorage`.

## Testing

Components using `t()` or `useLocale()` need `IntlProvider` in the tree. Use `render` from `@/testing/test-utils`, not Testing Library's `render` directly — `test-utils.tsx` already wraps `AppProvider` (and therefore `LocaleProvider`) around the component under test (see [tests.md](../standards/tests.md)).
