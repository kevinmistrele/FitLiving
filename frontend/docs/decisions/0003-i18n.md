# 0003 - Internationalization with react-intl, owned per feature

## Context

The base needed an i18n solution. A sibling production app (internal, not public) already solved this with `react-intl` plus a hook (`useTranslate`) wrapping `useIntl().formatMessage`, and — critically — with each feature/module owning its own translation files instead of one shared catalog.

## Decision

- Adopt `react-intl` (`IntlProvider`, `useIntl`).
- Each feature that has UI copy owns `src/features/<feature>/i18n/{en,pt}.json` + `index.ts`.
- `src/i18n/feature-registry.ts` is the single place that imports every feature's messages and merges them; `src/i18n/index.ts` exposes the merged catalog and `SupportedLocale` type.
- `src/i18n/locale-provider.tsx` resolves the initial locale (`?locale=` → `localStorage` → browser language → `en`) and exposes `changeLocale` via context.
- `src/hooks/use-translate.ts` and `src/hooks/use-locale.ts` are the only sanctioned way components read/change translations — never import `react-intl` or `@/i18n` directly from feature code.
- Keys are flat and namespaced by feature (`"welcome.reload"`), not nested objects — avoids key-collision and diffing pain across features.

## Consequences

- Deleting a feature deletes its translations with it; no orphaned keys in a shared file.
- `src/i18n/feature-registry.ts` is an explicit, documented exception to the "shared folders can't import features" rule (see `docs/architecture/dependency-rules.md`) — by design, not an oversight.
- Adding a feature means also adding one line to `feature-registry.ts`; this is a manual step, same category as adding an ESLint zone per feature (see `docs/architecture/feature-template.md`).
- API-sourced data is never routed through `t()` — only static UI copy is. This must stay a convention every feature follows, since nothing enforces it mechanically.
